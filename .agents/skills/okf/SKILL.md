# okf

Open Knowledge Format (OKF) v0.2 is a minimal, open format for representing knowledge as a directory of markdown files with YAML frontmatter. It is designed to be authored by people, generated by agents, exchanged across organizations, and consumed by both.

## Overview

A knowledge bundle is a self-contained, hierarchical collection of concept documents. Each concept is a single markdown file with a YAML frontmatter block and a free-form markdown body. The format standardizes the small set of structural conventions needed to make a knowledge corpus self-describing — provenance, trust, lifecycle, and attestation — without prescribing any runtime or tooling.

Core concepts:

- **Bundle** — a directory tree of `.md` files, the unit of distribution
- **Concept** — a single knowledge unit, one markdown file
- **Concept ID** — the file path with `.md` suffix removed
- **Provenance** — `sources` frontmatter recording where a concept derives from
- **Trust** — `generated` and `verified` frontmatter recording how content was produced and confirmed
- **Lifecycle** — `status` and `stale_after` frontmatter tracking currency
- **Attested Computation** — a concept type carrying a sanctioned computation a consumer can verify

## Bundle Structure

```
bundle/
  index.md                      # Optional. Directory listing for progressive disclosure.
  log.md                        # Optional. Chronological history of updates.
  <concept>.md                  # A concept at the bundle root.
  <subdirectory>/               # Subdirectories organize concepts into groups.
    index.md
    <concept>.md
```

**Reserved filenames** — `index.md` and `log.md` have defined meaning and MUST NOT be used for concept documents. All other `.md` files are concepts.

## Concept Documents

Every concept is a UTF-8 markdown file with two parts:

1. **YAML frontmatter** — delimited by `---` at the start and a closing `---`
2. **Markdown body** — free-form content after the frontmatter

### Frontmatter

**Required:**

- `type` — a short string identifying the kind of concept (e.g., `Document`, `Report`, `Policy`, `Playbook`, `Reference`, `Attested Computation`). Not registered centrally; consumers MUST tolerate unknown types.

**Recommended:**

- `title` — human-readable display name
- `description` — single-sentence summary
- `resource` — canonical URI for the underlying asset (absent for abstract concepts)
- `tags` — YAML list of short strings for cross-cutting categorization

**Optional families:** provenance (`sources`), trust (`generated`, `verified`), lifecycle (`status`, `stale_after`), computation fields (§10). Producers MAY include any additional keys; consumers MUST NOT reject documents with unrecognized fields.

### Body Conventions

No required sections. These headings have conventional meaning when applicable:

- `# Schema` — structured description of an asset's columns/fields
- `# Examples` — concrete usage examples, often as fenced code blocks
- `# Computation` — the sanctioned computation of an Attested Computation

### Minimal Example

```markdown
---
type: Document
title: Q3 Sales Report
description: Quarterly sales summary with regional breakdown and year-over-year comparison.
resource: https://docs.acme.com/reports/2026/q3-sales.pdf
tags: [sales, quarterly, report]
---

# Summary

Covers North America, EMEA, and APAC regions. Key figures sourced from the
regional dashboards and cross-checked against the finance ledger.

# Key Figures

| Region   | Revenue   | Growth  |
|----------|-----------|---------|
| NA       | $4.2M     | +12%    |
| EMEA     | $3.1M     | +8%     |
| APAC     | $2.7M     | +22%    |
```

## Provenance, Trust, and Lifecycle

All optional. Their absence carries meaning — an unverified concept is distinguishable from a verified one but is never rejected.

### Provenance: `sources`

Records the materials a concept derives from, external or internal to the bundle.

```yaml
sources:
  - id: annual-report
    resource: https://www.acme.com/investors/annual-report-2026.pdf
    title: ACME Annual Report 2026
    author: human:finance-team
    last_modified: 2026-05-30
  - id: policy-doc
    resource: /references/safety-policy-v3.docx
    title: Safety Policy v3
    author: human:legal
    last_modified: 2026-04-15
  - id: api-spec
    resource: https://api.acme.com/openapi/v3.json
    title: ACME API v3 Specification
    last_modified: 2026-06-01
```

Each entry: `resource` is REQUIRED. `id`, `title`, `author`, `usage_count`, `last_modified` are optional. `usage_window` is a sibling of `sources`, framing every `usage_count` with a `{ from, to }` date range.

**Per-claim attribution** uses markdown footnotes keyed to `sources[].id`:

```markdown
Revenue recognition follows the accrual method as defined in section 4.2.[^annual-report]

[^annual-report]: ACME Annual Report 2026
```

### Trust: `generated` and `verified`

`generated` records how the current content was produced. `verified` records who or what has confirmed it.

```yaml
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
verified:
  - { by: human:ahormati, at: 2026-06-25T09:00:00Z }
  - { by: process:finance-nightly, at: 2026-06-26T02:00:00Z }
```

- `generated.by` is REQUIRED within `generated`. `generated.at` is an ISO 8601 datetime.
- `verified` is a list of `{ by, at }` mappings. A single verifier MAY be written as a bare mapping without the list dash; consumers MUST treat it as a one-element list.

### Trust Tiers

Derived from `verified`:

- No `verified` key → **unverified**
- `verified` by non-`human:` actors only → **machine-confirmed**
- `verified` by a `human:<id>` actor → **human-reviewed**

### Lifecycle

```yaml
status: stable        # draft | stable | deprecated
stale_after: 2026-09-23   # absolute date; content is stale on/after this day
```

Absent `status` implies `stable`. `stale_after` is optional; a concept is stale when `today >= stale_after`.

### Actor Convention

Fields recording identity (`generated.by`, `verified[].by`) use:

- `<producer>/<version>` for agents and tools (e.g., `reference_agent/gemini-2.5-pro`)
- `human:<id>` for a person (e.g., `human:ahormati`)
- `process:<id>` for automated processes (e.g., `process:finance-nightly`)

Producers MUST use `human:` prefix for hand-authored or human-confirmed content.

## Index Files

`index.md` MAY appear in any directory. It enumerates directory contents for progressive disclosure. Contains no frontmatter, except bundle-root `index.md` MAY carry `okf_version: "0.2"`.

```markdown
# Reports

* [Q3 Sales Report](reports/q3-sales.md) - Quarterly sales summary with regional breakdown
* [Annual Financial Summary](reports/annual-financial.md) - Year-end financial overview

# Policies

* [Subdirectory](policies/) - Safety and compliance policies
```

Entries SHOULD include the description from the linked concept's frontmatter.

## Log Files

`log.md` MAY appear at any level to record change history. Flat list of date-grouped entries, newest first:

```markdown
# Directory Update Log

## 2026-05-22
* **Update**: Added [Q3 Sales Report](/reports/q3-sales.md) with regional breakdown.
* **Creation**: Established the [Safety Policy v3](/policies/safety-v3.md) from the updated DOCX source.
```

Date headings MUST use ISO 8601 `YYYY-MM-DD` form. The leading bold word is a convention, not a requirement.

## Cross-linking

Concepts MAY link to other concepts using standard markdown links. Two forms:

- **Absolute (bundle-relative):** begins with `/`, interpreted relative to bundle root. Recommended — stable when documents are moved within their subdirectory.
- **Relative:** standard markdown relative path.

Consumers MUST tolerate broken links — a missing target is not malformed.

### The `references/` Convention

A `references/` subdirectory conventionally mirrors external material, run instructions, or code as first-class concepts within the bundle. Sources, executors, and attesters commonly point into it. It is a naming convention, not a requirement.

## Attested Computations

An Attested Computation concept (`type: Attested Computation`) carries a sanctioned way to compute a value so a consumer can confirm the value was produced correctly.

### Contract Fields

- `runtime` — REQUIRED. How to run the computation (e.g., `python`, `postgres`, `bigquery`, `dbt`, `Looker`).
- `parameters` — list of typed, named holes: `{ name, type, required }`. Binding semantics follow `runtime`.
- `computation` — optional path to a file holding the computation. Absent → the body `# Computation` fenced code block is the computation.
- `executor` — `resource` names run instructions; `receipt` declares fields a run must return.
- `attester` — `resource` names deterministic code (no LLM) that takes a receipt and returns a verdict.

### Example

```markdown
---
type: Attested Computation
title: Revenue for fiscal year
description: Recognized revenue for a fiscal year, per Finance's definition.
status: stable
runtime: postgres
parameters:
  - { name: year, type: integer, required: true }
executor:
  resource: references/run-sql.md
  receipt: [query_id, executed_sql, result]
attester:
  resource: references/attesters/revenue.py
generated: { by: reference_agent/gemini-2.5-pro, at: 2026-06-20T22:53:05Z }
verified: { by: human:ahormati, at: 2026-06-25T09:00:00Z }
stale_after: 2026-09-23
sources:
  - id: rev-policy
    resource: https://wiki.acme/finance/revenue-recognition
    title: Revenue recognition policy
---

# Computation

    SELECT SUM(amount) AS revenue
    FROM recognized_revenue
    WHERE fiscal_year = $1

The computation binds only the declared `parameters`.[^rev-policy]

[^rev-policy]: Revenue recognition policy
```

A concept that uses a computation stays one readable document and links to the Attested Computation:

```markdown
---
type: Metric
title: Revenue
description: Recognized revenue for a fiscal year.
---

# Definition

Recognized revenue, computed by [the revenue computation](../computations/revenue.md).
```

## Conformance

A bundle is conformant with OKF v0.2 if:

1. Every non-reserved `.md` file contains a parseable YAML frontmatter block
2. Every frontmatter block contains a non-empty `type` field
3. Reserved filenames (`index.md`, `log.md`) follow their specified structure when present

Consumers MUST NOT reject a bundle because of: missing optional fields, unknown `type` values, unknown additional keys, broken cross-links, or missing `index.md` files.

## Versioning

This skill targets OKF version **0.2**. Bundles MAY declare `okf_version: "0.2"` in a bundle-root `index.md` frontmatter block.

## Gotchas

- **URL sources often need multi-page scraping** — when a source URL points to a landing page, the agent must follow sub-links and scrape content across pages to build a complete OKF concept. Record each visited URL as a separate `sources` entry so provenance traces back to every page used.
- **PDF and office file sources are opaque** — the agent extracts text/structure from the file and records the file path or URL as `sources[].resource`. The extracted content becomes the concept body; the original file stays referenced, not inlined.
- **`type` is the only always-required frontmatter field** — a concept carrying just `type` is fully conformant. Do not invent required fields beyond what the spec defines.
- **`index.md` has no frontmatter** — except at the bundle root where `okf_version` is permitted. Do not add `type`, `title`, etc. to index files.
- **`log.md` has no frontmatter** — it is a pure markdown file with date-grouped entries.
- **`verified` bare mapping is valid** — `verified: { by: human:ahormati, at: 2026-06-25T09:00:00Z }` is equivalent to a one-element list. Normalize to list form when merging entries.
- **`sources[].resource` is required within each source entry** — but `id`, `title`, `author`, etc. are all optional. Do not require them.
- **`usage_window` is a sibling of `sources`, not inside entries** — it frames every `usage_count`. A single entry MAY carry its own `usage_window` to override.
- **Per-claim footnotes use `sources[].id` as the label** — not positional indices. The footnote label is the join key; agents rewrite documents and positional indices misattribute silently.
- **`stale_after` is an absolute date, not a TTL** — consumers compare `today >= stale_after` with no reference to when the concept was read.
- **Absent `status` implies `stable`** — do not assume `draft` or `deprecated` when the field is missing.
- **Cross-links use standard markdown** — the relationship kind (references, depends-on, joins-with) is conveyed by surrounding prose, not by the link itself.
- **`references/` is a convention, not a requirement** — do not enforce it. It is a common place for executors, attesters, and external material.
- **Broken links are not errors** — consumers MUST tolerate them. A link to not-yet-written knowledge is valid.
- **Attested Computation is its own concept** — do not inline computation contract fields into a Metric or Table concept. Keep them separate and link.
- **The agent supplies only parameter values** — it MUST NOT author or edit the computation itself. Binding parameters into the executable artifact is the consumer's job.
- **`generated` and `verified` are independent** — content can change without re-confirmation, and facts can be re-confirmed without regeneration. Keep them distinct.
- **`verified` confirms the definition; attestation confirms a run** — a concept with a stale definition can still attest cleanly, and a freshly-verified definition still requires attestation on each run.
