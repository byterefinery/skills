# Route Handlers and Middleware

## Route Handlers

`route.ts`/`route.js` files are the lowest-level routing primitive: raw HTTP in, raw HTTP out.

- Location: anywhere in `app/`, conventionally `app/api/...`. `app/api/users/route.ts` → `/api/users`.
- Named exports for each verb: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD` — each receives `(request: NextRequest, context)`.
- **No caching by default.** In 15, `GET` handlers are dynamic unless you opt in: `export const dynamic = 'force-static'` or `export const revalidate = 3600` in the route file. Other verbs are never cached, even next to a cached `GET`.
- A `route.ts` and `page.ts` **cannot share a directory** — each file claims all verbs for its path. Route Handlers do not participate in layouts or client-side navigation.
- Context typing: `RouteContext<'/users/[id]'>` (types generated by `next dev`/`build`/`typegen`); `await ctx.params` in 15.

```ts
import type { NextRequest } from 'next/server'

export async function GET(_req: NextRequest, { params }: RouteContext<'/users/[id]'>) {
  const { id } = await params
  return Response.json({ id })
}
```

- Return a `NextResponse`/`Response`, or `null` to let a downstream rewrite/`_document` handle it.
- `NextRequest` extends `Request` (has `nextUrl`, `cookies`). **`.geo` and `.ip` were removed in 15** — the host supplies those.
- `NextResponse` extends `Response` (has `redirect()`, `rewrite()`, `next()`, `revalidate()`, `withCookies()`, `json()`, `empty()`).
- Set `Cache-Control` headers to control CDN behavior of cached handlers.
- For work that should not block the response (analytics, logging, webhooks), use `after(() => ...)` from `next/server` (stable since 15.1).
- `userAgent(request)` from `next/server` parses the request's user agent into structured data (`{ isBot, browser, device, engine, os, cpu }`) — handy in middleware for per-device rewrites.
- Special metadata route files (`sitemap.ts`, `opengraph-image.tsx`, `icon.tsx`, ...) remain static by default unless they use Dynamic APIs.

## Middleware

`middleware.ts` (or `.js`) at the project root (or in `src/`, next to `app/`/`pages/`). Runs before a request completes; only **one per project** (split logic into imported modules). Defaults to the **Edge runtime**; since **15.5** it can run on the **Node.js runtime** by exporting the runtime in its config:

```ts
// middleware.ts — Node.js runtime (15.5+)
export function middleware(request: NextRequest) {
  // full Node.js API available here
  return NextResponse.redirect(new URL('/home', request.url))
}
export const config = {
  matcher: '/about/:path*',
  runtime: 'nodejs',   // omit for the Edge runtime (default)
}
```

```ts
// Edge runtime example — locale rewrite
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'

export function middleware(request: NextRequest) {
  const url = request.nextUrl.clone()
  url.pathname = '/en' + url.pathname
  return NextResponse.rewrite(url)
}

export const config = {
  matcher: ['/about/:path*', '/dashboard/:path*'],
}
```

- Use cases: redirects, rewrites (A/B tests, locale routing), header injection, auth checks that end in a redirect/rewrite, responding directly.
- Not suitable for: slow data fetching, session management, anything heavy — it's on the hot path.
- `fetch` caching options (`cache`, `next.revalidate`, `next.tags`) **have no effect** in middleware; middleware fetches are always uncached.
- `matcher` is a string, string array, regex, or array of objects (with `regex` or `path`/`has` keys); patterns support `:path*` suffixes. To exclude paths, use a negative pattern like `((?!api|_next/static|_next/image|favicon.ico).*)`. Matcher values must be constants (statically analyzed at build time).
- Cookies are readable/settable via `request.cookies` and `response.cookies`; setting a cookie here re-renders the route with the new value.
- Middleware works with both `app/` and `pages/` routers, including `output: 'export'` (runs at build/request per platform support).

## Config-based routing (next.config.js)

Often simpler than middleware for static rules — apply to every matching request without runtime code:

```js
const nextConfig = {
  headers: async () => [{ source: '/(.*)', headers: [{ key: 'X-Frame-Options', value: 'DENY' }] }],
  redirects: async () => [
    { source: '/old', destination: '/new', permanent: true },
  ],
  rewrites: async () => [
    { source: '/docs/:path*', destination: '/blog/:path*' },
  ],
}
```

- `rewrites` have three phases: `beforeFiles` (before filesystem), `afterFiles` (after, default), `fallback` (last resort, no static file check).
- Precedence on a request: `redirects` → `beforeFiles` rewrites → filesystem (`app/`/`pages/`) → middleware → `afterFiles` → headers → `fallback` → not found. (Exact ordering varies by phase; test with `next build -d` verbose output.)
- `next/experimental/testing/server` (15.1+) exposes `unstable_getResponseFromNextConfig` to unit-test headers/redirects/rewrites without a server.
